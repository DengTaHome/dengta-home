# 真机验证（本地构建 + 生产后端 + 真浏览器）

单测回答「代码符合假设吗」，这个脚本回答**「用户到底能不能看到」**。

它在真 Edge、390×844 移动视口、真账号登录态下检查关键界面，失败会以非零码退出。

## 为什么需要它

在本项目里它抓到过两个所有单测都放过的 bug：

1. **心潮胶囊被渲染成嵌套 `<button>`** —— 无效 HTML，浏览器重排出一大块灰色方块压住状态栏。
   单测只断言组件能渲染，看不到合成后的布局。
2. **`drives` 数据形态不匹配** —— 线上返回对象 `{ possess: 0.79, … }`，而 `sortDrives` 只认数组，
   于是花瓣一片都不画、主导项永远回退成「心潮」。单测喂的是数组，所以一直绿。

## 检查项（任何一条不过就退出码 1）

1. 应用外壳渲染
2. 有实质内容（说明真的登录了）
3. 心潮胶囊在状态栏内
4. 心潮花瓣 ≥ 1 片
5. 心潮胶囊有尺寸
6. 状态栏高度为 68（线上一致）
7. 滑动高亮块已挂载
8. 拒答标注样式已加载
9. 部分回复样式已加载
10. 没有嵌套 `button`（无效 HTML）
11. 无 console 错误

## 局限

- 依赖生产后端可用（免费实例冷启动时首次会很慢，脚本已等 12 秒）
- 只覆盖首屏与状态栏；聊天流、投屏、音乐播放需要真实动作，尚未纳入

# 流式渲染场景（verify-streaming.mjs）

拦截 `/chat/stream`，喂一段合成 SSE（含 `meta` → `status` → 三段正文 → `done`，
其中一段故意只用旧的 `text` 字段），验证渲染过程不产生 `undefined`、没有未捕获异常。

```powershell
node tools/browser-verify/verify-streaming.mjs
```

## 它能证明什么

- 请求契约被真的走到（拦截计数 ≥ 1）
- F-4 回归：末段用 `text` 字段时，界面**不会**出现字面量 `undefined`
- 整轮没有未捕获异常

## 它不能证明什么（重要）

**无法验证「流式过程中逐字渲染」。** 原因：`done` 之后前端会用服务端真相校正消息列表，
合成消息会被真实历史覆盖；而 Playwright 的 `route.fulfill` 只能一次性返回整段 body，
无法模拟真实的慢速分块。要验证逐字显示，需要真实后端 + 真实发一条消息（会花额度）。

这个限制是刻意写下来的：**不要用它冒充「逐字显示已验证」**。

# 私密媒体设置端到端（verify-media-e2e.mjs）

回答一个具体抱怨：「在设置里换了头像，聊天里没变」。

```powershell
node tools/browser-verify/verify-media-e2e.mjs
```

完整链路并断言：

1. 上传一张临时头像（`public/app-icon-192.png`）→ 201
2. 设为 `user_avatar` 偏好 → 200，且目录读回时偏好指向新资产
3. 真浏览器加载 → 聊天里出现 `img.message-avatar-image`，`naturalWidth > 0`，
   并且确实请求了 `/api/v2/private-media/assets/<id>/content`
4. **清理**：清空偏好 + 永久删除临时资产，目录回到 0 个 active

实测结论：**头像链路是通的**（请求了内容，渲染出 192×192 的 blob 图片）。

## 这个脚本最该记住的一件事

第一版把静态服务器放在 **5188 端口**，结果浏览器里消息一条都没渲染、
头像请求一个都没有，看起来像「重大 bug」。真实原因是
**后端 CORS 白名单只放行 5173**，所有接口被浏览器拦掉了。

> 端口不对 → 假 bug。测出来的「异常」先检查测试环境本身。

# 界面稳定性（verify-stability.mjs）

用户说状态栏会「错位、闪」。这个脚本不靠肉眼，测两件事：

1. **布局位移（CLS）**：累计无输入位移得分
2. **状态胶囊/状态栏位置采样**：每 250ms 一次，外壳出现 2 秒后位置不应再变

```powershell
node tools/browser-verify/verify-stability.mjs
```

## 当前实测

| 指标 | 结果 | 判定 |
| --- | --- | --- |
| 状态胶囊位置（2 秒后） | 52 次采样只有 1 种取值 | ✓ 不跳 |
| 状态栏容器位置 | 1 种取值 | ✓ 不跳 |
| CLS（首次） | **0.1159** | ✗ 超过 0.1「需要改进」线 |
| CLS（重复访问） | **0.116** | ✗ 同上 |
| 重复访问首条消息 | 726–7,525 ms（波动大） | 取决于后端 |

## 结论：闪的不是状态栏

状态栏本身**完全稳定**（52 次采样零位移）。CLS 的唯一来源是
`.message-list` 在 5–8 秒时从空状态变成 43 条消息，
位移源是 `message-row`。

把缓存上限从 40 提到 60 **没有**降低 CLS（仍 0.116），
说明「预览条数少于真实历史」不是主因。下一轮继续找替换瞬间的真正位移原因。
## CLS 归因（第二轮）

对比「缓存预览」与「真实历史」渲染后的行数、行高和滚动位置：

```
预览      44 行，高度和 11,895，scrollH 12,469，scrollTop 11,889（贴底）
+160ms    44 行，高度和 12,070（字体加载）
+2.9s     44 行，高度和 12,201，scrollTop 11,889 → 12,015
+3.5s     scrollH 12,595 → 12,675，scrollTop 12,015 → 11,961
```

三点结论：

1. **行形状不是原因。** 把 `visible_monologue`、`music_card` 等影响行高的字段补进缓存后，
   高度和仍然是 11,895 → 12,201，CLS 仍是 0.1159。
2. 位移来自**替换瞬间的滚动位置校正**：`scrollTop` 先补偿 +126，随后又回退 −54，
   与 `scrollHeight` 的增长不同步，可见行因此被推着动。
3. 下一轮的攻击点：替换时的滚动锚定（谁来 pin 到底部、什么时候 pin）。
## 一次假通过（重要）

同一台机器上曾出现「CLS 通过」的结果，但那次 `重复访问首条消息` 是 **121 秒**，
页面其实一直停在加载态——**什么都没渲染，自然没有布局位移**。

原因是脚本直接用 `_audit/browser/auth.json` 里的 token，而它 1 小时就过期，
过期后所有接口 401，应用停在加载遮罩。

已修：脚本现在会检查 `expires_at`，过期就用账号密码向 Supabase 换新 token。
教训写进这里——**「指标变好」也可能是测量环境坏了**，看到异常好的数字先看陪伴指标。

## 第三个被证伪的假设：浏览器滚动锚定

关掉 `.message-list` 的 `overflow-anchor`（实测计算样式确认生效为 `none`）后，
CLS 仍然是 **0.1159**，一分不差。所以既不是条数、不是行高、也不是浏览器锚定。

# 一键实机体检（run-all.mjs）

```powershell
node tools/browser-verify/run-all.mjs
```

依次跑六个真机脚本并输出汇总。四个硬性脚本阻断，界面稳定性目前非阻断（CLS 仍略超 0.1）。

## 这一轮学到的四件事（都已写进脚本）

1. **本地请求不能走代理。** 原来所有请求都经 `127.0.0.1:10809`，包括 `127.0.0.1:5173` 的自己。
   第二个标签页会卡满 120 秒超时。现在统一加 `bypass: "127.0.0.1,localhost"`。
2. **取 token 会偶发失败。** 代理会返回 `upstream request timeout`，
   脚本现在重试三次（非 async 上下文里用同步退避）。
3. **固定等待会误判。** 原来是「等 12 秒再看」，慢后端下会把正常页面判成「没登录」。
   现在等 `.message-bubble` 真的出现（最多 90 秒）再判定。
4. **断言失败必须反映到退出码。** 媒介验证曾经打印「设置未生效」却以 0 退出——
   和之前 token 过期导致的「CLS 假通过」是同一类错误。

## 环境不健康时先修环境

`run-all` 跑之前会探测后端 `/health`，连续三次失败就直接退出并提示：
**这一步失败时不要下「产品有问题」的结论。**
## 前端测试为什么老是「挂起」

会话里多次出现 `frontend:tests` 跑着跑着停住、CPU 归零。定位结果：

`test:design-polish` 里那一段 `node --test` 一次并行跑了 16 个测试文件，
其中多个会各自启动 Vite；并行时它们抢同一个 WebSocket 端口（日志里出现过
`Port 24678 is already in use`），谁先失败谁就卡住不退。

单跑 `memory-summary-lifecycle.test.js` 只要 31 秒、45 条全过，所以不是测试本身的问题。

已在该段加 `--test-concurrency=1`，之后完整验证一次跑通（1607 条）。

## 一个还没答案的产品疑点

在**全新浏览器存储**（无聊天缓存、无恢复数据）里加载应用时，
自动化观察到：应用停在欢迎/导航界面，不自动选中任何会话，也不报错
（所有接口 200、console 无错误）。29 个会话在后端确实存在。

有缓存时反而正常：缓存把上次会话喂给 `activeSessionId`，聊天立刻渲染。

下一轮要确认：这是「新设备首次打开」的预期欢迎页，还是自动选中会话的逻辑有缺口。
`refreshSessions()` 里确实有「没有 preferredId 就选第一个会话」的逻辑，
需要查它在启动路径上到底有没有被调用。

## 「不自动选中会话」的答案

之前的疑点解开了：**不是缺陷**。

全新存储打开时，应用自动选中的是**会话列表第一个**，而它可能是个空会话
（页面显示「小小灯当前模型：auto」的空状态）。后端 29 个会话都在，
`mergeRecoveredStartupData()` 也确实执行了「没有指定会话就取第一个」。

测量脚本不能假设第一个会话有历史。现在稳定性与媒体两个脚本都会
**主动点开会话、直到出现消息**，再开始测量。

连带两个后果：

1. 之前「重复访问 121 秒」是假数字——那个空会话永远出不了消息，
   脚本一直等到 120 秒超时。
2. 之前的 CLS 0.116 里混进了「脚本点击侧边栏会话」造成的位移。
   现在在选好会话之后**清零位移记录**再测，CLS 达标（<0.1）。

按 CLS 规范，用户输入引起的位移本来就不该计入；脚本的模拟点击不算真实输入，
所以必须显式清空，而不是把点击位移也算成产品问题。
