## 二、首屏与回复速度

同一台机器、同一后端，连续构建实测：

| 阶段 | 重复访问「第一条消息」 |
| --- | --- |
| 起点 | 6,542 ms |
| 移除 7.4 MB 字体预加载 + preconnect | 8,502 ms（首次路径），重复路径 4,010 ms |
| 加聊天历史缓存 | 4,010 ms |
| **放开加载占位（isLoading）** | **766 ms** |

关键发现：缓存数据早已在内存里，却被「正在加载 DengTa home…」的占位符挡着。
把占位条件改成「有可显示消息就不显示占位」后，收益从 39% 提升到 88%。

冷启动（首次安装）仍需 8–11 秒：26 个 API 分三波，每波 2–4 秒，属网络往返成本。
本地 JS 长任务合计仅 204 ms——**代码不慢，慢在网络**。

## 七、已知未完成（需要人或环境）

2. **仓库的三个迁移在生产库不适用（已查证，不是「未执行」）**：
   - 生产库的迁移版本是时间戳格式（`20261018023642`…），不是仓库的 001–070 编号；

   - `companion_runtime_states` 只有 6 列，`status`/`interaction_stats` 两个 jsonb；
     bootstrap 返回的 `state` 正好来自这张表（含 `revision: 593`）
   - 全库列名扫描（drives/emotion/consciousness/partial/is_streaming/draft…）只命中
     `music_playback_queue.revision`，**没有任何心潮或流式中间态列**
   - 063 的两件事线上已完成：8 张表 `rowsecurity = true`，
     且 `anon`/`authenticated` 对它们都没有 SELECT 权限
   - 关键补充：`messages` 共 19 列，其中含
     `chat_generation_state`（text）+ `chat_generation_started_at` / `_lease_expires_at` /
     `_failed_at` / `_completed_at` 四个时间戳 + `client_message_id`（uuid）

## 八、测量本身的教训

这一轮抓到的产品缺陷里，有两个是「测量工具先说谎」：

- token 过期 → 页面没渲染 → 却报「CLS 达标」；
- 页面在慢后端下没加载完 → 却报「设置未生效」。

所以每次「指标突然变好/变坏」，都要先看**陪伴指标**是否自相矛盾
（例如「CLS 0.0000 但首条消息 121 秒」）。这条已写进工具 README。

### 平台清理的一次误删与修复（2026-10-28）

清理 GitHub Releases 时我犯了一个错误：58 个 release 的 `created_at` **全部相同**
（`2026-10-18T08:25:23Z`，批量创建），我却按 `created_at` 排序取"最新 10 个"，
结果删掉了 v2.12.4–v2.12.18 这些**真正最新的版本**，留下了 v2.11.0–v2.12.3。

为什么没有丢数据：删之前已逐个核对本地备份，48 个待删 APK 的大小与 GitHub 记录完全一致、
ZIP 魔数正常，`backup\releases\` 里 58 个 APK 全在。

修复结果：15 个最新版本（v2.12.4–v2.12.18）已从本地备份重新发布，全部成功；
复核 25 个 release 的资产大小与本地备份完全一致，`v2.12.18` 实测可下载（HTTP 206）。
净效果：58 个 release / 2,277.9 MB → **25 个 / 984.1 MB**，回收约 1.29 GB，
同时保住了全部最新版本。

审计记录保留这次错误，不删除。

**教训（以后批量删除前必须做的检查）**：

1. 排序键必须**唯一且单调**。`created_at` 相同意味着这批数据不是按时间生成的，
   不能当作版本新旧依据。
2. 版本类数据按 **semver** 排，不按时间排。
3. 删除前做一次「反向断言」：要删的集合里**不许出现**最大/最新版本。
   这次如果有这条断言，就不会误删。

### 语音输入链路（2026-10-28 第二轮）

**结构问题**：麦克风原本只存在于输入框「+」菜单的第二层，用户要先点加号才看得到
「长按说话」。语音是高频入口，不该埋在二级菜单。

改动：

| 项目 | 之前 | 现在 |
| --- | --- | --- |
| 语音入口 | 「+」菜单第二层 | 输入框操作行一级按钮（菜单旧入口保留） |
| 按下行为 | 无 | 立即触发 `/voice/warmup` 预热（30 秒节流） |
| 输入框布局 | 3 列网格 | 4 列（附件 / 输入 / 语音 / 发送），窄屏 40px |
| 松手反馈 | 无 | `navigator.vibrate(12)`，录音开始已有 18 毫秒震动 |

**后端延迟**（`/voice/turn`）：

- 设置读取与「按 session 找到会话」改为并行发出；模型解析仍在转写之前，
  保留「无效模型不消耗语音转写额度」的既有约束。
- 回复落库后的 `touchConversation`、主动消息评估、自主动态评估、记忆压缩
  原先逐个 `await`，现在改为 `res.json` 之后后台执行。
  响应里的 `memory_compression` 因此固定为 `null`（前端从未消费该字段）。

**情绪理解**：

- 置信度新增软区间（0.45–0.62）：此前低于 0.62 就直接丢弃情绪类别；现在
  可以把它当「很弱的线索」交给模型，同时明确禁止说出类别或据断言。
- 上游返回中文或同义词（开心 / 疲惫 / Joyful 等）时归一到固定八类；
  真正未知的类别仍然拒绝，不猜测。

**音频格式适配**：部分安卓 WebView 录出的 blob 没有 `type`，此前上传后
服务端只收到 `application/octet-stream`。现在前端显式补 `audio/webm`，
后端再按文件扩展名做一次兜底归一。

**验证**（全部真机浏览器，非推断）：

- `verify-voice-ui.mjs`：假麦克风真实触发录音，验证预热请求、录音态计时、
  两次震动、最终收敛（回复或可读错误），10 项全过
- `verify-layout-matrix.mjs`：6 个安卓视口，含新增「输入框不得窄于 120px」检查，0 问题
- `verify-startup-recovery.mjs`：唤醒横幅可见性 3 视口全过
- `verify-streaming.mjs`：流式契约全过
- 全量单测：前端 / 后端在本轮改动后重新跑通

**踩到的两个坑（记录以免重犯）**：

1. 把补丁 CSS 追加到 `apple-ui.css` 尾部，结果落进未闭合的 `@media` 里，只在部分宽度生效。
   → 修法：独立顶层文件 + 花括号配平测试。
2. 语音按钮的 `aria-label` 写成「长按说话，松开发送」，其中「发送」二字让
   流式验证的 `button[aria-label*="发送"]` 选中了麦克风，看起来像流式功能坏了。
   → 修法：麦克风标签改为「长按说话」，验证脚本改用 `.send-button` 类名。
